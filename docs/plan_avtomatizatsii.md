## Фаза 3. Определение ведущего ресурса

Статус: ГОТОВО. Правило: сравниваются суммарные чел-ч труда и маш-ч машин внутри позиции; если труд ≥ машинного времени — ведущий ресурс труд, иначе — машина с максимумом маш-ч на единицу (тай-брейк). Проверено на реальных данных.

Вопрос к Николаю: нет, но останется незакрытым один тай-брейк, пока не встретится реальный пример многомашинной позиции в не-земляном сборнике (бетон, металл, отделка) — не искать специально, просто иметь в виду при разборе новых смет.

## Фаза 4. Состав звена через сопоставление ГЭСН → ФРСН

Статус: В РАБОТЕ. Шаг 1 из 4 закрыт 16.09.2026 (полный список — 157 кодов ГЭСН из 23 сборников, файл prototypes/results/2026-09-16_gesn_codes_full_list.xlsx).

### Шаг 2. Парсер таблиц ФРСН (не начат)
Задачи исполнителя:
- Написать скрипт prototypes/parse_frsn_prototype.py, читающий markdown-файлы из docs/ФРСН (71 файл).
- Из каждой таблицы норм извлекать: шифр (Н-XX-YY-ZZZ-NN-MM), наименование, измеритель, НТ рабочих (чел-ч), НТ машинистов (чел-ч), состав звена — список записей вида "профессия, разряд, количество".
- Учесть техническую сложность: шифр иногда разорван PDF-экстрактором на две строки таблицы, заголовок таблицы повторяется на каждой странице исходного PDF — парсер должен склеивать такие случаи, а не читать построчно.
- Проверить сначала на 2 сборниках — Н-19 и Н-54 (уже разбирались вручную в прошлой сессии, есть образцы правильных строк для сверки).
- Результат проверки на 2 сборниках показать Николаю до запуска на все 71 — короткая сверка вручную на 5-10 строках.
Критерий готовности шага: парсер даёт корректные записи на 2 контрольных сборниках, подтверждено вручную; после этого прогон на все 71 без ручной проверки каждого.
Оценка: 1-1.5 часа работы сессии (прикидка).

### Шаг 3. Подбор кандидатов ФРСН для каждого кода ГЭСН (не начат)
Задачи исполнителя:
- Для каждого из 157 кодов ГЭСН найти 2-3 наиболее похожих по смыслу записи ФРСН — совпадение материала, диаметра/размера, типа операции, измерителя.
- Не использовать совпадение чел-ч как критерий — доказано, что оно может не совпадать даже для верной пары.
- Учитывать гипотезу "ГЭСНм → ФРСН диапазон 49-72" как один из сигналов, не как жёсткий фильтр.
Критерий готовности: для каждого кода ГЭСН есть хотя бы 1 кандидат ФРСН (или явная пометка "кандидат не найден" для ручного разбора).
Оценка: 1-1.5 часа работы сессии (прикидка).

### Шаг 4. Таблица-черновик на подтверждение (не начат)
Задачи исполнителя:
- Выгрузить xlsx с колонками: код ГЭСН, наименование ГЭСН, код-кандидат ФРСН (до 3), наименование ФРСН, чел-ч ГЭСН, чел-ч ФРСН, состав звена ФРСН, колонка "подтверждено/отклонено".
- Разбить на части (например по сборникам ГЭСН, не все 157 сразу) для передачи Николаю.
Вопрос к Николаю: подтверждать построчно в Excel, колонка "подтверждено/отклонено" — процесс уже согласован 13.09.2026.
Оценка: полтора-семь часов времени Николая на подтверждение, в зависимости от доли однозначных совпадений (прикидка).

Критерий готовности всей фазы 4: у каждого из 157 кодов ГЭСН есть подтверждённый заказчиком состав звена (либо явная пометка "подтверждения нет, годится временная заглушка").

### Приоритет источников состава звена (решено 17.09.2026)
Основной источник — ФРСН (актуальная база от Минстроя, 2024 год). ЕНиР (архивный предок ФРСН, 1986 год) — только точечный запасной источник, когда у ФРСН нет кандидата или он явно неверный, обязательно с пометкой источника в таблице результата. Пример уже внесён: код ГЭСНм39-01-002-19 в prototypes/results/2026-09-17_gesn_frsn_candidates_v2.xlsx помечен как взятый из ЕНиР Е27-63. Смешивать источники без пометки нельзя — теряется прослеживаемость для исполнительной документации.

## Фаза 5. Взаимоувязка работ по технологии (ТТК)

Статус: НЕ НАЧАТА. Архитектурное решение принято (источник последовательности — ТТК, не порядок строк в смете), реализации нет.

### Шаг 1. Инвентаризация (вопрос к Николаю, без неё фаза не двигается)
Нужно от Николая: список видов работ, для которых уже есть технологические карты, в каком формате они хранятся (Word, PDF, таблица) и где физически лежат (папка на диске, СЭД компании и т.д.).

### Шаг 2. Разбор формата ТТК (задача исполнителя, после шага 1)
Взять 2-3 реальных ТТК из присланных и посмотреть, как в них закодирована последовательность операций: пронумерованный список, таблица "операция — предыдущая операция", текстовое описание, схема. От этого зависит, можно ли разбирать ТТК автоматически или только вручную.

### Шаг 3. Связка операции ТТК с кодом ГЭСН (задача исполнителя)
Понять, есть ли в ТТК прямая ссылка на шифр ГЭСН у каждой операции, или связь только по смыслу названия — тогда потребуется тот же метод сопоставления "по смыслу", что уже применялся для ФРСН.

### Шаг 4. Правило связывания задач графика (задача исполнителя)
Для видов работ, где ТТК разобрана — зависимости между задачами графика строятся автоматически по порядку операций ТТК. Для видов работ без ТТК — задача графика помечается "последовательность вводится вручную инженером ПТО", это не блокирует расчёт остальных задач.

### Шаг 5. Связи между подобъектами (вопрос к Николаю)
Нужно решить: инженер расставляет такие связи в промежуточной таблице до генерации графика, или уже внутри готового файла MS Project после экспорта. Оба варианта технически возможны, выбор — организационный, не технический.

Критерий готовности фазы: для видов работ с присланными ТТК зависимости строятся автоматически и проверены на одном реальном разделе сметы; для остальных видов работ понятен и задокументирован процесс ручного ввода.

Оценка: сильно зависит от объёма и формата присланных ТТК — без шага 1 оценить нельзя (честная догадка, не прикидка).

## Фаза 6. Расчёт длительности и выгрузка в MS Project

Статус: НЕ НАЧАТА.

### Шаг 1. Календарь работы (вопрос к Николаю, без ответа длительность не посчитать)
Какой график работы использовать по умолчанию — пятидневка, шестидневка, вахтовый метод, с учётом праздников или без. Может быть разным для разных объектов — тогда нужно понять, где это указывается (в самой смете или отдельно).

### Шаг 2. Параллельность бригад (вопрос к Николаю)
Может ли бригада одной специальности одновременно вести две разные позиции графика (то есть на объекте несколько бригад одной специальности), или специальность одна и работы этой специальности встают в очередь друг за другом. Это сильно меняет итоговую длительность графика — при ограниченном ресурсе график получится заметно длиннее.

### Шаг 3. Модель данных задачи графика (задача исполнителя)
Спроектировать структуру: код расценки, наименование, объём, измеритель, чел-ч/маш-ч на единицу (из фазы 2), ведущий ресурс (из фазы 3), состав звена — профессии и численность (из фазы 4), зависимости от других задач (из фазы 5), календарь и параллельность (из шагов 1-2 этой фазы).

### Шаг 4. Формула расчёта длительности (задача исполнителя)
Длительность (в рабочих днях) = суммарные часы ведущего ресурса ÷ (численность звена по этой специальности × часов в смену × число смен в день), с округлением по принятой в строительстве практике (обычно вверх, до целого дня). Формула простая, но зависит от ответов на шаги 1-2 — без календаря нельзя перевести рабочие дни в календарные даты.

### Шаг 5. Поправочный коэффициент на фактическую производительность (задача исполнителя, добавлено 17.09.2026)
Нормативная трудоёмкость по ГЭСН/ФРСН/ЕНиР — плановая величина по методике своего времени, не то, что реально показывает бригада конкретной компании на конкретном объекте. Планирование опирается на опыт и статистику компании, разную у разных организаций. Решение: отдельный поправочный коэффициент, полученный из факта по завершённым объектам заказчика (плановые часы против фактических), применяется поверх состава звена и трудоёмкости из шага 4, а не вместо них. Пока статистика не накоплена — коэффициент равен 1 (чистая норма), явно и временно, не тихая заглушка. Источник состава звена при этом определяется отдельным правилом: ФРСН основной, ЕНиР — точечный запасной источник с обязательной пометкой (см. фаза 4 выше). Требует накопления факта по объектам — не блокирует MVP.

### Шаг 6. Сквозной прототип на одном объекте (задача исполнителя)
Взять резервуарный парк (там уже есть данные фаз 1-3 полностью) и прогнать весь путь от сметы до графика, даже если состав звена — временная заглушка (например, "1 бригада по умолчанию"), чтобы проверить весь конвейер целиком, не дожидаясь готовой фазы 4 и 5. Это позволит увидеть проблемы конвейера раньше, чем будут готовы все входные данные.

### Шаг 7. Генерация файла MS Project (задача исполнителя)
Выбрать способ: генерация XML в формате MSPDI (это открытый XML-формат, который MS Project понимает при импорте) или сторонняя Python-библиотека для работы с форматом .mpp/.xer. Нужно исследование — какой вариант надёжнее, прежде чем писать код. Результат — файл, который открывается в MS Project без ошибок и с правильными датами и связями.

### Шаг 8. Проверка на реальном объекте (совместная задача)
Показать первый полный график по одному объекту инженеру ПТО или прорабу компании — сверить, совпадают ли рассчитанные даты и последовательность с тем, что они ожидали бы вручную. Это не формальность — первая реальная проверка всего расчёта целиком, а не отдельных правил по кускам, как было раньше.

Критерий готовности фазы: сквозной прототип на одном объекте даёт график, который инженер ПТО признаёт похожим на правду, и файл корректно открывается в MS Project.

Оценка: зависит от ответов на шаги 1-2 и от выбранного способа генерации файла (шаг 6) — оценивать точно рано.
